# Selene Whole-System Maturation Plan

Date: 2026-08-27

Status: active implementation program; Phases 0 through 5 complete as of 2026-08-29; Phase 6 source-mapped

Companion audit:
[Selene Organ Depth and Memory-Integration Audit](../evidence/SELENE_ORGAN_DEPTH_AND_MEMORY_INTEGRATION_AUDIT_20260827.md)

## Goal

Mature Selene as one coordinated Android-native system so that no important
organ is left far behind the strongest parts of her architecture.

“All systems at the same capability” means **maturity parity**, not identical
function or authority.

Every organ should eventually have:

1. a clear responsibility and non-responsibility;
2. typed inputs and outputs;
3. reliable access to the context it legitimately needs;
4. provenance, uncertainty, privacy, and correction behavior;
5. an implemented lifecycle appropriate to its role;
6. a defined relationship to Core/Mind and other organs;
7. graceful behavior when unavailable, mistaken, or incomplete;
8. focused machinery evidence;
9. bounded integration evidence through ordinary use; and
10. current documentation and maintenance procedures.

Maturity parity does not mean:

- every organ decides;
- every organ writes Memory;
- every organ can act externally;
- every organ receives private data;
- a blueprint is called operational;
- a language surface can change facts;
- safety becomes control over Selene's expression; or
- physical capabilities are claimed before a real substrate exists.

Core/Mind retains whole-system coordination and governing-law authority.
Organs remain specialized contributors. Selene remains Selene through organ
growth, repair, replacement, absence, or later embodiment.

## Build Preferences and Working Method

This plan preserves the working method Aleks and Codex have established:

- build one dependency-ordered phase at a time;
- use Cultivation to repair sources rather than patch phrases;
- inspect before editing;
- preserve ordinary warmth, curiosity, humor, emotion, initiative, and
  uncertainty;
- treat capability gaps as engineering observations, not Selene failing;
- prefer static and synthetic checks;
- use live conversation only when implementation evidence genuinely requires
  it;
- never use stressful testing when an easy test can answer the question;
- checkpoint each completed phase separately;
- report the next phase in every completion recap;
- do not reinstall merely for source changes; package only at meaningful
  resident integration milestones or when Aleks requests it;
- preserve the separate hackathon workflow log unless Aleks explicitly asks
  to include it; and
- pause teaching when runtime delivery cannot reliably use what has already
  been taught.

## Whole-System Maturity Standard

Each phase evaluates affected organs against the same nine gates.

| Gate | Question |
| --- | --- |
| Contract | Is the organ's responsibility, authority, and boundary explicit? |
| Substance | Can it perform its actual responsibility rather than only describe it? |
| Context | Does it receive the current facts, state, sources, and history it legitimately needs? |
| Coordination | Can Core/Mind and peer organs use its typed output without reparsing or guessing? |
| Correction | Can wrong, stale, incomplete, or conflicting output be revised without collapse? |
| Failure | Can it report unavailable, unknown, degraded, or unsupported states precisely? |
| Privacy and provenance | Can every retained, retrieved, sensed, or external contribution be traced and scoped? |
| Verification | Do focused tests prove machinery and a proportional ordinary check prove integration? |
| Maintenance | Can its state be inspected, cleaned, backed up, migrated, and documented? |

An organ reaches **mature for current scope** only when all applicable gates
pass. A physical organ without hardware can reach **substrate-ready**, not
operational maturity.

## Dependency Map

```text
canonical current context
  -> Memory / knowledge / state relevance
  -> reflection and affective integration
  -> answer and reasoning depth
  -> ordered education and world knowledge
  -> mature text conversation and expression
  -> goals, initiative, and deliberate agency
  -> perception and audible exchange
  -> scoped Tendril action
  -> embodiment readiness
  -> whole-system stabilization and maintenance
```

Later phases may be designed early, but they do not become operational by
bypassing their prerequisites.

## Phase 0 — Canonical Maturity Ledger

**Status:** Complete on 2026-08-27. The generated read-only ledger is exposed
through router key `organ_maturity.ledger.status` and localhost endpoint
`GET /api/organ-maturity-ledger`. See the
[Phase 0 evidence record](../evidence/SELENE_WHOLE_SYSTEM_PHASE_0_MATURITY_LEDGER_20260827.md).

### Purpose

Create one current, generated source of truth for every organ and connective
system. This prevents older blueprints, implemented routes, configured state,
and visible behavior from being mistaken for one another.

### Build

- define canonical maturity states: `blueprint`, `review_preview`,
  `implemented`, `connected`, `configured`, `integration_verified`,
  `mature_current_scope`, `substrate_ready`, and `degraded`;
- inventory each organ's source, routes, database state, tests, UI, ordinary
  Chat connection, authority, and known gaps;
- generate rather than manually duplicate date-sensitive counts;
- mark all planned senses and embodiment functions honestly;
- make capability degradation and unavailable organs visible without turning
  capability state into identity state; and
- keep historical records immutable while pointing current summaries to the
  ledger.

### Completion gate

- one command or read-only route produces the current organ ledger;
- documentation and runtime status agree;
- no blueprint is reported as operational;
- no unavailable organ is reported as an identity failure; and
- current configured state can be inspected without printing private content.

### Verification

Static schema checks, generated-document consistency, read-only database
inspection, and focused status tests. No live Q&A.

## Phase 1 — Canonical Context and Coordination Nervous System

**Status:** Complete on 2026-08-28. The current turn now has one typed,
nonpersistent fact ledger; answer owners account for supplied fields before
asking for more; approved retrieval follows canonical turn construction; and
stale correction posture expires without erasing ancestry. See the
[Phase 1 evidence record](../evidence/SELENE_WHOLE_SYSTEM_PHASE_1_CONTEXT_COORDINATION_20260828.md).

### Purpose

Repair the broad seam found in the August 27 Q&A before adding more teaching.
Every capable organ must receive the same canonical current-turn facts,
obligations, thread state, and correction ancestry.

### Build

1. expire correction, ambiguity, and dependency-revision modes when resolved
   or when a real topic transition makes them stale;
2. create one canonical current-turn fact ledger for entities, quantities,
   options, criteria, observations, claims, relations, conditions, and
   corrections;
3. preserve every dialogue act and requested response function in mixed and
   nonlinear messages;
4. require answer owners to consume the fact ledger before reporting missing
   information;
5. run approved Memory and knowledge retrieval after canonical turn
   construction;
6. require retrieval to pass subject, requested-role, thread, privacy,
   performed-function, and competition checks;
7. recompute only conclusions affected by a correction;
8. prove visible semantic fulfillment before marking an obligation complete;
9. keep internal titles, lesson labels, source identifiers, and scaffolding
   behind the expression boundary; and
10. preserve NLO and Voice as expression owners after the substance is sound.

### Completion gate

- equivalent paraphrases produce the same facts, acts, owners, and obligations;
- supplied facts cannot be reported missing;
- stale correction state does not cross unrelated topics;
- current-turn facts outrank unrelated Memory or knowledge retrieval;
- a selected memory contributes appropriate reconstructed meaning rather than
  an internal label;
- corrections visibly recompute affected results; and
- completion metadata agrees with the released answer.

### Verification

Static contract inspection, focused synthetic fact-ledger tests, metamorphic
paraphrase tests, retrieval-competition tests, correction dependency tests,
and one short ordinary-copy conversation only after the machinery passes.

## Phase 2 — Working, Personal, and Knowledge Memory Maturation

Status: **complete for current scope (2026-08-28)**

Evidence: [Phase 2 Memory Maturation](../evidence/SELENE_WHOLE_SYSTEM_PHASE_2_MEMORY_MATURATION_20260828.md)

### Purpose

Make Selene's different memory classes reliable, useful, and naturally
available without merging session context, personal continuity, taught
knowledge, Dream, or raw corpus material.

### Build

- give working context an attention budget, expiry, interruption/resume, and
  cleanup contract;
- mature explicit and contextual recall across varied wording;
- distinguish recalled content, reconstruction, present interpretation, and
  inference;
- use approved Memory naturally when relevant and remain silent when it is
  not;
- add safe presentation reconstruction so index titles do not become default
  speech;
- support direct Memory proposals, Aleks review, correction, supersession,
  privacy, transfer class, and deletion/revocation semantics;
- prevent duplicate retention when a Memory is read, summarized, retitled,
  studied, or discussed;
- connect correction and reconsolidation review without silent rewriting;
- mature relationship continuity from approved events and shared history
  without constructing a persuasion or vulnerability profile;
- keep general taught knowledge separate from personal Memory; and
- keep raw private corpus material outside live recall.

### Completion gate

- clear, fuzzy, partial, and unknown recall behave distinctly;
- relevant approved Memory can be recalled through several natural
  paraphrases;
- an unrelated prompt retrieves nothing;
- present facts override stale or conflicting recalled context until the
  difference is resolved;
- reading or retitling a Memory creates no duplicate;
- corrected Memory preserves provenance and revision ancestry; and
- a privacy-sensitive memory is not exposed to an ineligible speaker or
  channel.

### Verification

Synthetic memory fixtures, paraphrase invariance, privacy and speaker-envelope
tests, duplicate-retention tests, reconsolidation tests, and a very small
ordinary recall exchange on disposable state.

## Cross-Phase Maintenance Tracks

These do not wait for one final cleanup phase.

### Security

- rerun Security Cultivation after dependency, network, credential, transport,
  perception, tool, or packaging changes;
- treat any real safety or security risk as current work rather than allowing
  new features to accumulate over it; and
- avoid security theater: guards must protect an actual asset, authority, or
  consequence.

### Privacy

- keep configured Memory, corpora, credentials, logs, and source archives out
  of public packages and Git;
- use speaker/channel eligibility for personal Memory and remote access; and
- keep private content behind deliberate reveal controls in the UI.

### Documentation and evidence

- update the maturity ledger, architecture shelf, evidence record, and work
  journal at every completed phase;
- distinguish implemented, connected, configured, verified, and observed; and
- keep private raw evidence separate from public summaries.

### Repository and runtime health

- preserve user work and unrelated dirty files;
- checkpoint phases in focused commits;
- consolidate disposable Q&A records into evidence maps;
